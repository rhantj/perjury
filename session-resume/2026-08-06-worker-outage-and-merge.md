## 배포본이 LLM을 전혀 안 쓰고 있었다

푸시하려고 `main`을 받다가 발견했다. 같은 날 B가 올린 **1-A(추첨)**가 `GameView`에
`responderIds`를 더했는데, 워커 화이트리스트를 함께 넓히지 않았다.

```
배포된 워커에 실제 요청 →  HTTP 400
  {"code":"invalid_request","message":"rounds[0]: 허용되지 않은 필드 'responderIds'"}
```

워커는 모르는 키를 **거부**한다(`workers/src/schema.ts`의 `onlyKeys`). 첫 라운드 기록이
생기는 순간부터 모든 판단 요청이 튕겼다. 게임은 끝까지 갔지만(폴백은 살아 있었다)
**좌석 대사가 전부 사전생성 문장**이었다. 심사자가 봤다면 AI가 없는 게임으로 보였을 것이다.

`schema.ts`에 이미 이 함정에 대한 경고가 적혀 있었다 — 「워커를 먼저 배포하고 프론트를
나중에」. 순서가 뒤집힌 것이다.

**고친 방법**: `findings`·`powerSpent`와 같은 관용 파싱(없으면 빈 배열). 그래야 어느
순서로 배포해도 창이 닫힌다. 회귀 테스트 3개를 붙여 같은 일이 되풀이되면 워커 테스트가
먼저 깨지게 했다. `npm run worker:deploy` 완료.

**`npm run worker:typecheck`도 이미 깨져 있었다.** 같은 원인이다.
**아직 안 고친 것: CI가 워커를 안 본다.** `.github/workflows`는 `npm run build`
(메인 tsconfig)만 돌린다. 워커 타입체크·테스트를 CI에 넣을 값이 있다.

## 엔진 작업을 1-A 위로 리베이스해 통합했다

앞 스냅샷의 세 커밋(2-A 능력 대기 · 3-A 조기 고발 · 3-B 탈락자가 잃는 것)을
`origin/main` 위로 리베이스했다. 충돌 세 곳을 손으로 풀었다.

- `progress.test.ts` · `challenge.test.ts`의 import — 양쪽 합집합
- `docs/위증-룰개편-정리-2026-08-06.md` — 양쪽이 같은 경로에 새로 만들어 통째로 충돌.
  **B의 §5 표를 뼈대로 쓰고**(1-A/1-B 구분과 담당 표기가 더 정확하다) 거기에 상태 열과
  §4의 결정·보류 근거를 얹었다. B가 쓴 「1단계를 A/B로 쪼갠 이유」 주석 블록은 그대로 살아 있다.

리베이스 뒤 테스트 하나가 전제를 잃어 고쳤다 — 「탈락해도 반증은 사람이 한다」가
`advanceToHuman`이 반증 페이즈에 선다고 가정했는데, 추첨에서 사람이 빠지면 그냥 지나간다.
`suggestAll`로 배치를 직접 세워 의도(뽑혔으면 탈락해도 사람이 선언한다)를 보존했다.

**능력 대기가 이제 진짜 목적대로 검증된다.** 추첨은 다섯 중 둘만 뽑으므로 지목한 상대가
빠질 확률이 3/5다. 그 경로를 진짜 `suggest`로 도는 테스트를 새로 넣었다
(`power.test.ts`의 「verify-claim — 추첨에서 빠진 좌석」).

## 다음에 여기부터

### 1. 결정이 먼저인 것 둘 — 3-C 착수 전

리뷰가 잡았고 [결정 011](../docs/decisions/011-조기-고발과-탈락자.md)의
「아직 안 정한 것」에 적어뒀다. 둘 다 **탈락자 손패로 가는 문**이다.

- **검시관(`inspect-hand`)이 탈락자를 지목할 수 있다.** 결정 011이 탈락자에게 밀담을 막은
  근거(「틀려도 정보원이 하나 생긴다」)와 같은 문인데 이쪽만 열려 있다.
- **탈락자를 이의제기로 잡으면 그 사람 손패가 1장 열린다.** 막으면 탈락자가 벌 없이
  위증하는 오염원이 되므로 단순히 막을 일은 아니다.

지금은 엔진이 막지 않고, **논란 있는 쪽을 테스트로 고정하지도 않았다.**

### 2. 3-C — 시야·워커·AI·UI

**순서가 강제된다.** `workers/src/schema.ts`의 `gameView` 화이트리스트에 `'eliminated'`를
관용적으로 추가하고 **워커부터 배포**한 뒤 `src/engine/view.ts`의 반환 객체에 넣는다.
반대로 하면 이번 장애가 그대로 재현된다.

UI에서 하나 주의: `Verdict.tsx`의 「본인」 라벨. 지금까지 `accuser.kind === 'player'`는
사람 시민의 최종 고발뿐이라 항상 맞았는데, `accuseEarly`가 처음으로 **AI가 accuser인
결과**를 만든다(범인 자백 · AI 시민의 조기 고발). `playerId`와 뷰어를 비교해야 한다.

### 3. 수치는 여전히 보류 — 1-B에 종속이다

라운드 24와 밀담 6은 「추첨 2인 **· 비공개**」 전제로 부록 B에서 유도한 값이다.
1-A만 들어간 지금 넣으면 24제안 × 0.8장 = 19장분이 열리는데 손패는 12장뿐이라
후반에 여전히 다 드러난다. **1-B가 들어간 뒤에 한 커밋으로 올린다.**

### 4. 2-B — 변호사·협잡꾼 대기

`round.ts`의 `declareAll` 안에 있다. 1-B가 같은 함수를 또 건드리므로 그 뒤에 얹는다.

## 팀에 전달 (B에게)

- **시야에 필드를 더할 때는 워커를 먼저 넓히고 먼저 배포한다.** 위 장애가 그것 때문이다.
  `npm run worker:typecheck`는 **CI가 안 돌리므로** 손으로 돌린다.
- **`round.ts`의 `suggest`에 한 줄 들어갔다**(탈락자 거부). `declareAll`은 안 건드렸다.
- **`GameState`에 `eliminated: readonly PlayerId[]`가 늘었다.** `createGame`이 `[]`로 채운다.
- **룰 개편 문서 §5 표에 상태 열을 붙였다.** 1-B 담당이 아직 미정이고, 그게 proxy 스코프를
  건드리므로 착수 전에 정해야 한다.
- **§3-4의 「이의제기 현재 3회」는 낡았다.** 코드는 이미 2회다(결정 008).
- **라운드 24는 워커 호출 캡에 걸린다.** 배포된 워커가 `IP_DAILY_CALL_CAP=120`,
  `DAILY_CALL_CAP=250`(둘 다 기본값)인데 한 판이 약 120회다. 한 사람이 하루 한 판이면
  IP 예산이 소진되고 그 뒤로는 폴백만 보인다. 올리려면 API 비용 결정이 필요하다.
