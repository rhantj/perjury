# 트러블슈팅 6선

막혔던 것 중 여섯 개를 골랐다. 고른 기준은 **해결의 난이도가 아니라 사고 과정이 드러나는가**다.
처음 세운 가설이 틀렸던 것, 에러 메시지가 원인을 가리키지 않았던 것, 코드가 아니라 환경이 문제였던 것 순이다.

실패한 시도를 지우지 않았다. 틀린 길을 먼저 갔다는 사실이 이 기록의 절반이다.

## 1. 예산 카운터가 동시 호출에서 80% 샜다

**2026-08-03 · Infra · High · 해결 (설계 변경으로 우회)**

### 증상

Cloudflare Workers 프록시에 하루 호출 캡을 걸었는데 캡이 걸리지 않았다.
반증 5건을 동시에 보내면 카운터가 1만 올라갔다.

```
호출 5건 → 남은 예산 241 → 240   (236이어야 맞다)
```

같은 구간에서 타임아웃도 함께 났다.

```
POST /decide 504 Gateway Timeout (25067ms)  × 5
```

### 원인

- **표면** — 예산 카운터가 호출 수를 실제보다 적게 셌다.
- **근본** — `chargeCall`이 **읽고 → 쓰는** 구조라 5개 요청이 전부 같은 값을 읽고 각자 +1을 썼다.
  전형적인 read-then-write 경합이다. 실측 누수 약 **80%**.

**틀렸던 전제가 여기 있다.** 설계 문서 §6.3에 "몇 회 새는 것은 허용"이라고 적어뒀었다.
그 문장은 호출이 무작위로 흩어진다는 가정 위에 있었는데, 실제 우리 호출 패턴은
**매 라운드 반드시 5개가 동시에 나가는 구조적 충돌**이었다. 확률이 아니라 구조였다.

타임아웃은 별개 원인이 아니라 같은 구조의 다른 얼굴이었다. 단독 호출은 11초인데
로컬 GPU가 하나라 5개가 줄을 서서 25초 상한을 넘었다.

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| 누수를 허용 범위로 보고 넘어가기 | 기각 | 캡 250에 실제 ~1,250회가 나갈 수 있다. KV 쓰기도 5배라 무료 한도(1,000/일)를 넘긴다 |
| 타임아웃 상한만 올리기 | 기각 | 원격 모델이 느려도 같은 일이 난다. 지연에 취약한 구조 자체는 그대로다 |

### 해결

락을 걸지 않았다. **호출 구조를 바꿔 동시성 자체를 없앴다.**
반증 판단을 규칙 기반으로 유지하고 LLM에는 대사 생성만 맡겼다.

- 판당 호출 **50 → 15**
- 동시 호출이 사라져 경합과 타임아웃이 동시에 없어졌다
- 반증 판단은 원래 기계적("제안된 3장 중 내 손에 있는 게 있나")이라 품질 손실이 작다

### 남은 리스크

카운터의 read-then-write 자체는 그대로다. 지금은 동시 호출이 없어서 안 드러날 뿐,
호출 구조를 바꾸면 재발한다. 근본 해결은 Durable Objects 같은 직렬화 지점을 두는 것이다.

### 배운 점

**"몇 건 새도 된다"는 허용치는 호출 패턴을 알기 전에는 쓸 수 없다.**
그리고 가장 좋은 동시성 해결책이 동시성을 없애는 것일 때가 있다 —
락을 거는 대신 호출을 3분의 1로 줄이자 두 문제가 같이 사라졌다.

## 2. 폴백이 LLM 장애를 숨겨 「대사만 안 뜨는」 것으로 보였다

**2026-08-04 · 외부 API · High · 해결**

### 증상

LLM이 완전히 죽었는데 **게임은 끝까지 정상으로 굴러갔다.** 화면상으로는 "대사만 안 뜬다"로 보였다.

네트워크 탭은 더 헷갈렸다. 실패 신호가 어디에도 없었다.

```
POST /decide 200
POST /decide 200
POST /decide 200
```

### 원인

두 겹이었다.

1. **폴백이 제 일을 너무 잘했다.** 절대 규칙 4(폴백 경로를 깨지 않는다)대로 사전생성 대사로
   조용히 넘어가서, 게임이 정상 동작하는 것처럼 보였다.
2. **HTTP 상태 코드가 실패를 안 알렸다.** `/decide`는 200을 돌려주고 **본문이 `ok:false`**였다.
   프론트는 본문의 `ok`를 보고 던지는데, 네트워크 탭만 보면 전부 성공이다.

브라우저 콘솔에서 `fetch`를 감싸 응답 **본문**을 찍어보고서야 드러났다.

```js
const orig = window.fetch
window.fetch = async (...a) => {
  const r = await orig(...a)
  if (String(a[0]).includes('/decide')) r.clone().json().then((j) => console.log(j))
  return r
}
```

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| 네트워크 탭에서 실패 요청 찾기 | 실패 | 전부 200이다. 실패가 본문에만 있었다 |
| 콘솔 에러 확인 | 실패 | 폴백이 예외를 삼키고 정상 경로로 갔다 |

### 해결

**폴백 사유 배너(`fallbackReason`)를 먼저 구현했다.** 편의 기능으로 분류돼 있던 것을
진단 장치로 재분류한 것이다. `budget`과 `error`를 나눈 이유는 복구 가능성이 다르기 때문이다 —
`error`는 다음 라운드에 나을 수 있지만 `budget`은 그날 안에 낫지 않는다.

### 이후

당시에는 200 + `ok:false` 규약을 그대로 뒀고, "새로 붙는 호출부가 상태 코드만 보면 같은 함정에
빠진다"를 남은 리스크로 적었다. 그 리스크는 이후 없앴다 — 지금 `/decide`의 실패 경로는
전부 비-200이다(400·403·429·502·503·504). 계약은 [`docs/api-contract.md`](api-contract.md)에 있다.

프론트가 여전히 `code`를 읽는 이유는 따로 있다. 같은 `503`이라도 `budget_exhausted`와
`not_configured`는 사용자에게 다른 말을 해야 하기 때문이다.

### 배운 점

**잘 만든 폴백은 장애를 감추는 장치이기도 하다.** 가용성을 위해 넣은 것이 진단을 막았다.
심사 중에 조용히 폴백으로 떨어졌다면 아무도 모른 채 넘어갔을 것이다.
그래서 폴백에는 "지금 폴백이다"를 드러내는 표시가 한 세트로 따라와야 한다.

그리고 **HTTP 200은 성공을 뜻하지 않는다.** 애플리케이션 레벨 실패를 본문에 담는 API에서는
네트워크 탭이 거짓말을 한다.

## 3. 연속 푸시가 GitHub Pages 배포를 잠갔다

**2026-08-06 · CI · Medium · 우회 (근본 원인은 추정)**

### 증상

빌드는 통과하는데 배포 잡만 죽었다. 라이브 링크가 이전 커밋에 멈췄다.

```
Created deployment for 385356dcf8a850635d9a2c22006cc55e1df7ca70
Getting Pages deployment status...
##[error]Deployment cancelled.
```

`queued → in_progress → failure`를 18초 만에 반복했다. 재실행해도 같았다.

### 원인

- **표면** — `deploy` 잡의 `actions/deploy-pages@v4`가 취소됨.
- **근본 (추정)** — `deploy.yml`의 `concurrency.cancel-in-progress: true` 때문에 짧은 간격의
  연속 푸시가 진행 중인 Pages 배포를 여러 번 끊었다(실행 목록에 `cancelled` 6건).
  Pages 배포는 중간에 끊기면 환경에 잠금이 남을 수 있다.

**확인한 것과 추정한 것을 나눠 적는다.**

- 확인함 — 빌드 산출물은 매번 정상, Pages 설정도 정상(`build_type: workflow`, source `main`),
  `typecheck`·`build`·테스트 497건 전부 통과. 우리 코드 문제가 아니다.
- 확인 못 함 — 잠금이 실제로 남았는지는 GitHub 측 상태라 확인 수단이 없었다.
  위 근본 원인은 **정황 근거에 의한 추정**이다.

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| 워크플로 재실행 | 실패 | 같은 지점에서 같은 방식으로 취소됨 |
| 빌드 산출물 점검 | 이상 없음 | 원인이 빌드 쪽이 아니었다 |

### 해결

**근본 해결이 아니라 운영 방식으로 우회했다.** 여기서 멈춘 것을 숨기지 않는다.

- 시간을 두고 다시 시도
- 필요하면 빈 커밋으로 새 빌드를 태운다 (`git commit --allow-empty`)
- **연속 푸시를 삼간다** — 한 번 올리고 끝날 때까지 기다린다

배포 후에는 라이브 번들 해시를 로컬 빌드와 대조해 실제로 반영됐는지 확인한다.

### 배운 점

**푸시가 곧 배포인 구조에서는 푸시 빈도 자체가 인프라 변수다.**
로컬에서 빠르게 여러 번 커밋·푸시하는 습관이 배포 파이프라인에서는 경합이 된다.

그리고 **"우리 코드 문제가 아니다"를 증명하는 데도 근거가 필요했다** — 빌드 산출물 정상,
설정 정상, 테스트 통과를 하나씩 확인하고서야 외부 요인으로 판단을 옮길 수 있었다.

## 4. 같은 모서리를 쓰는 절대배치 셋이 서로를 덮었다

**2026-08-05 · FE · Low · 해결 (1차 수정이 틀린 뒤)**

심각도는 Low지만 여기 넣은 이유는 **처음 세운 가설이 두 번 틀렸기 때문**이다.

### 증상

게임판 좌석의 좌상단에서 참가 번호(`나`, `1`, `2`…)를 상태 배지가 그대로 덮어 글자가 겹쳐 보였다.

에러는 없다. **타입체크·테스트·빌드가 전부 통과한 상태에서 화면에만 나타나는 종류다.**

### 원인

- **표면** — 배지가 번호 위에 그려진다.
- **근본** — 좌석(`.seat`)이 `position: relative`인 상태에서, **서로 다른 세 요소가 각자
  독립적으로 같은 모서리에 `position: absolute`로 놓여 있었다.**

  | 요소 | 좌표 |
  |---|---|
  | `.seat__face` (번호) | `top: 0.55rem; left: 0.65rem; width: 1.75rem` |
  | `.seat__turn-badge` (차례) | `top: 0.5rem; left: 0.6rem` |
  | `.seat__suggest-badge` (제안) | `top: 0.5rem; left: 0.6rem` |

  절대배치된 형제는 서로의 존재도 크기도 모른다. 각각 "좌석 왼쪽 위"라는 의도로 따로 작성됐고,
  세 규칙이 한 화면에서 만난다는 사실을 아무도 검사하지 않았다.

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| `.seat__suggest-badge`를 `left: 2.65rem`로 옮김 (번호칸 폭 + 간격 계산값) | 「제안」은 안 겹쳤지만 **「차례」가 그대로 겹쳐 재발** | 좌표 이동은 증상 하나만 없앤다. 같은 모서리를 쓰는 나머지는 그대로 남는다 |
| `.seat__turn-badge`를 미사용 CSS로 판단하고 삭제 제안 | **오진.** 사용자 스크린샷이 실제로 렌더되고 있음을 증명 | grep 패턴 `seat__badge`는 `seat__turn-badge`를 잡지 못한다. "검색 결과 0건"을 "안 쓰임"으로 결론냈다 |

### 해결

좌표를 조정하는 대신 **구조를 바꿨다.** 세 요소를 `.seat__tags` 하나로 묶고, 그 묶음만 절대배치한다.
안쪽은 flex 흐름에 맡기므로 배지가 몇 개 켜지든 나란히 놓인다 — 겹칠 자리가 없다.

```css
/* src/styles/game.css — 묶음만 절대배치, 안쪽은 흐름 */
.seat__tags {
  position: absolute;
  top: 0.55rem;
  left: 0.65rem;
  display: flex;
  align-items: center;
  gap: 0.3rem;
}
```

`.seat__turn-badge`·`.seat__suggest-badge`에서 `position: absolute; top; left`를 제거했다.
계산으로 만든 매직 넘버(`2.65rem`)도 함께 사라졌다.

커밋 `0f5ff78`(1차 — 좌표 이동, 불충분) → `d1718cd`(구조 수정) → merge `73b4447`.

### 검증

1차 수정이 불충분했던 것도 배포본을 눈으로 봐서야 드러났으므로, **배포본 육안 확인이 종결 조건**이었다.
강제 새로고침(⌘⇧R) 후 배지가 나란히 뜨는 것을 확인했다. CSS 변경은 브라우저가 옛 번들을 들고 있는
함정에 특히 잘 걸린다.

### 배운 점

**절대배치 요소들이 같은 모서리를 공유하면 좌표 조정은 증상 치료다.** 흐름 컨테이너로 묶어
"몇 개가 켜지든 나란히 놓인다"로 바꾸면 겹침이 구조적으로 불가능해진다.
버그 하나가 아니라 버그의 종류를 없애는 쪽을 골라야 한다.

그리고 **grep의 "결과 없음"을 "쓰이지 않음"으로 읽으면 안 된다.**
`seat__badge`로 검색하면 `seat__turn-badge`는 잡히지 않는다(부분일치 방향이 반대다).

## 5. 아무것도 덮지 않는 장식 레이어가 가로 스크롤바를 만들었다

**2026-08-05 · FE · Low · 해결**

### 증상

게임 화면에 가로 스크롤바가 생겼다. 넘치는 자식 요소는 눈에 띄지 않았다.

### 원인

- **표면** — `.stage`가 가로로 24px 넘쳤다.
- **근본** — `.seats--photo::before`의 `inset: -1.5rem`(=24px). 장식용 **의사 요소**가
  좌우로 bleed하면서 부모를 넘겼다. 의사 요소는 DOM 자식 순회에 잡히지 않는다.

배포본에서 직접 재서 범위를 좁혔다.

```
.stage  clientWidth 942  vs  scrollWidth 966   → 정확히 24px 초과
넘치는 일반 자식: 0개
.seats 좌/우 = 115 / 1051  ≡  .stage 좌/우 = 115 / 1051
```

측정에서 하나가 더 드러났다. **`.seats`는 이미 `.stage`를 좌우로 꽉 채우므로 좌우 bleed는
덮을 대상이 없다.** 왼쪽 넘침은 그냥 잘리고 오른쪽만 스크롤이 되니 **이득 0 · 스크롤바 1**이었다.

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| 넘치는 자식 요소 찾기 | 실패 | 일반 자식은 0개다. 범인이 의사 요소라 자식 순회에 안 잡혔다 |
| `overflow-x: hidden`으로 덮기 | **의도적으로 안 씀** | 넘침을 가리는 것이지 없애는 게 아니다. 원인이 남는다 |

### 해결

`inset: -1.5rem` → `inset: -1.5rem 0`. 좌우 bleed만 없앴다.
위아래 bleed는 실제로 좌석 줄 바깥까지 사진을 넓히는 효과가 있어 유지했다.

브라우저에서 이 규칙만 주입해 재측정 → `scrollWidth 942 === clientWidth 942`.

### 배운 점

**넘침 문제에서 `overflow: hidden`은 해결이 아니라 은폐다.**
그리고 **자식 요소를 순회해도 안 나오는 넘침은 의사 요소를 의심해야 한다.**
`clientWidth` vs `scrollWidth` 차이를 숫자로 재면 원인 범위가 한 번에 좁혀진다(정확히 24px = 1.5rem).

## 6. 착석하는 순간 화면이 검게 죽었다

**2026-08-16 · FE · Critical · 해결**

### 증상

브리핑에서 착석 버튼을 누르면 화면 전체가 검게 남고 앱이 멈춘다. 원탁이 아예 뜨지 않아
판을 시작할 수 없다. 콘솔에 예외가 한 번 찍힌다.

```
Error: Minified React error #310; visit https://react.dev/errors/310 for the full message or use the non-minified dev environment for full errors and additional helpful warnings.
    at jo (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:8:48780)
    at ls (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:8:55205)
    at Object.ds [as useEffect] (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:8:55427)
    at e.useEffect (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:1:7959)

    at Co (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:8:47520)
    at gc (http://localhost:4173/perjury/assets/index-CRtB_5hC.js:8:70002)
```

100% 재현. **배포본에서도 같았다** — 심사용 링크가 이 상태로 나가 있었다.

### 원인

- **표면** — `useEffect`가 던진다.
- **근본** — 훅 두 개가 **조기 return 아래**에 있었다.

```
595행  if (!store.state || !view)             return <Landing … />
599행  if (stage === 'briefing' || !scenario) return <Briefing … />
 …
710행  useEffect(…)   ← 제안 제한시간 타이머
735행  useEffect(…)   ← 만료 시 대신 제안
```

표지·브리핑을 그리는 렌더에서는 훅이 594행까지만 돌고, 원탁으로 넘어가는 렌더에서만 두 개가
더 돈다. React는 훅을 이름이 아니라 **호출 순서와 개수**로 식별하므로, 착석하는 순간
「이전 렌더보다 훅이 많다」가 되어 터진다. 에러 경계가 없어 트리가 통째로 언마운트되고,
그 결과가 검은 화면이다.

유입은 `4b9f404 feat: 제안에 60초 제한을 두고 만료 시 대신 제안한다`이고,
배포된 `946f00a`에 포함돼 있었다.

### 시도했지만 안 된 것

| 시도 | 결과 | 왜 안 됐는가 |
|---|---|---|
| **내가 방금 넣은 훅을 원인으로 의심** | 기각 | 승패 효과음용 `useEffect`를 583행에 막 추가한 참이라 그것부터 의심했다. 확인해 보니 조기 return **위**라 훅 순서를 바꾸지 않는다. 가설이 틀렸다 |
| 화면만 보고 판단 | 실패 | 표지·브리핑까지는 멀쩡히 뜬다. 화면 전환을 끝까지 밟기 전에는 아무 이상이 없다 |

**방향을 바꾼 지점**: 내 변경을 `git stash`하고 베이스라인을 다시 빌드해 같은 흐름을 재현했다.
번들 해시가 다른(`index-CRtB_5hC.js`) 베이스라인에서도 동일한 #310이 났다 —
이 시점에 「내가 만든 것이 아니다」가 확정됐다. 30초면 끝나는 확인이었다.

### 해결

훅 두 개와 그것들이 쓰는 값(`myMove`·`iAmOut`·`submit`·`timingSuggest`)을 조기 return **위로**
올렸다. return이 대신 해 주던 「원탁일 때만 돈다」를 조건이 직접 들게 했다.

```ts
const timingSuggest =
  view !== null &&
  stage === 'play' &&
  scenario !== null &&
  view.phase === 'suggest' &&
  myMove && !accusing && !iAmOut && !view.outcome
```

앞의 세 줄이 없으면 브리핑을 보는 동안 제안 타이머가 혼자 돌아 만료된다.
**조기 return을 없앤 게 아니라 그 몫을 조건으로 옮긴 것이다.**

### 검증

- 빌드·타입체크 통과, 단위 테스트 583개 통과
- 훅 호출 지점을 훑어 **마지막 훅(672행) < 조기 return(689행)** 확인
- 브라우저에서 착석 → 원탁 정상 렌더, 제안 → 추첨 → AI 반증 → 추리표 갱신까지 진행

### 추후 관리

`eslint-plugin-react-hooks`의 `rules-of-hooks`를 켜면 빌드 단계에서 잡힌다. 도입 검토 대상이다.
지금은 해당 지점에 이유를 적은 주석으로만 막아 두었다.

### 배운 점

**최소화 빌드의 에러 번호를 그냥 넘기지 말 것.** `#310`은 「훅 개수가 달라졌다」는 아주 구체적인
진술이라, 번호를 푼 시점에 원인 범위가 「조건부 훅」으로 좁혀졌다.

그리고 **「내가 방금 건드렸으니 내 탓」은 검증할 가설이지 결론이 아니다.**
이번엔 그 가설이 틀렸고, 베이스라인 재현이 그것을 30초에 갈랐다.
