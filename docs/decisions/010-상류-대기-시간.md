# 상류 대기 시간을 25초에서 15초로 줄인다

- 날짜: 2026-08-05
- 관련: [006-폴백-범위.md](006-폴백-범위.md), `workers/src/index.ts` `UPSTREAM_TIMEOUT_MS`, `src/ai/llm-decider.ts` `REQUEST_TIMEOUT_MS`

## 맥락

배포본에서 라운드가 한참 멈춘 것처럼 보이는 일이 있었다. 원인을 «상류가 느리다»로 짐작했지만,
고칠 방향이 셋(상한 늘리기 / 차단기 풀기 / 프롬프트 줄이기)이라 측정 없이 고를 수 없었다.

배포된 프록시에 실제로 호출을 넣어 쟀다(2026-08-05, 총 39건).

동시 호출 수를 바꿔가며(반증 판단):

| 배치 | 응답 시간 |
|---|---|
| 순차 3건 | 4.4 / 5.0 / 5.4초 |
| 동시 2건 | 5.0 / 6.2초 |
| 동시 3건 | 6.6 / 6.6 / 7.0초 |
| 동시 5건 × 3회 | 4.1~6.2초. 15건 중 1건만 25.6초에 504 |

판단 종류와 기록 길이를 바꿔가며(각 2건):

| 종류 | 짧은 기록(1R) | 긴 기록(8R) |
|---|---|---|
| suggest | 4.6 / 5.0초 | 4.2 / 4.3초 |
| refute | 5.1초, 1건 25.5초에 504 | — |
| challenge | 4.0 / 4.1초 | — |
| accuse | 4.2 / 7.7초 | 4.1 / 6.6초 |
| parley | 3.6 / 3.7초 | 4.3 / 4.3초 |

읽어낸 것은 넷이다.

1. **정상 응답은 4~8초다.** 가장 느린 정상 응답이 7.7초(accuse)였다. 25초 상한은 필요 이상으로 넉넉했다.
2. **동시 호출 수는 원인이 아니다.** 2건·3건·5건이 모두 같은 구간에 들어왔고,
   같은 5건 배치를 두 번 더 돌렸을 때는 낙오가 아예 없었다.
3. **판단 종류도, 기록 길이도 원인이 아니다.** 8라운드치 기록을 실은 호출(변동 입력 2,058토큰)이
   1라운드 호출보다 느리지 않았다. 프리픽스 캐싱이 도는 것도 같이 확인했다(캐시 1,433~1,474토큰 적중).
4. **낙오는 산발적이고, 상한을 다 쓰고 죽는다.** 39건 중 2건이 실패했고 둘 다 25.5초에 504였다.
   **8초와 25초 사이에 들어온 응답이 하나도 없다.** 이것이 이 결정의 근거다 —
   상한을 그 빈 구간 안으로 내리면, 살아 돌아올 응답을 자르지 않고 죽은 호출만 일찍 끊는다.

## 선택

상류 상한을 **25초 → 15초**, 프론트 상한을 **30초 → 20초**로 내린다.

한 라운드는 판단을 병렬(`Promise.all`)로 걷으므로 라운드가 끝나는 시각은 **가장 느린 한 건**이 정한다.
낙오 한 건이 나면 나머지 넷이 5초에 끝나 있어도 화면은 25초 동안 멈춰 있다.
정상 응답이 7초 안에 들어오는데 그 뒤 18초를 더 기다리는 것은, 이미 죽은 호출을 기다리는 시간이다.

15초는 정상 최대(7.7초)의 약 두 배다. 8라운드치 기록으로도 응답이 느려지지 않는 것을 확인했으므로
여유는 판이 길어져서가 아니라 **상류가 흔들릴 때를 위한 것**이다. 그래도 낙오는 10초 일찍 끊긴다.

**이 변경은 실패 건수를 늘리지 않는다.** 8~25초 구간에 응답이 없기 때문이다.
그래서 라운드 차단기(`ROUND_GIVE_UP = 2`, 결정 006)가 더 자주 내려갈 이유가 없다 —
잘리는 것은 어차피 폴백될 호출이고, 달라지는 것은 그 폴백이 오는 시각뿐이다.

프론트를 20초로 함께 내린 이유는 순서를 유지하기 위해서다. **프론트가 먼저 끊으면 상류 실패의 code가 사라진다.**
그러면 「예산 소진(budget)」과 「낙오(error)」를 구분하지 못해, 예산이 마른 판에서도 매 호출을 다시 던지게 된다.

## 버린 대안

- **상한을 늘린다.** 7초와 25초 사이가 비어 있으므로, 늘려서 건질 응답이 없다. 멈춰 보이는 시간만 길어진다.
- **차단기를 푼다(`ROUND_GIVE_UP` 2 → 3).** 차단기는 이미 결정 006에서 호출 단위로 좁혀 두었고,
  낙오 한 건은 그 좌석만 폴백된다. 여기서 더 풀면 회선이 정말 죽었을 때 페이즈마다 매달리는 시간이 늘어난다.
- **프롬프트를 줄인다.** 입력이 이미 캐시 1,433 + 신규 142다. 줄여서 얻을 것이 거의 없고,
  에이전트가 보는 정보를 깎는 대가가 크다.

## 되돌리는 법

두 상수를 되돌린다 — `workers/src/index.ts`의 `UPSTREAM_TIMEOUT_MS`(15_000 → 25_000)와
`src/ai/llm-decider.ts`의 `REQUEST_TIMEOUT_MS`(20_000 → 30_000). **둘은 같이 움직인다.**
프록시가 프론트보다 짧다는 순서가 깨지면 실패 code가 사라진다.
워커 쪽은 되돌린 뒤 `npm run worker:deploy`가 필요하다.

## 결과 (2026-08-13 확인)

**두 상수 모두 결정대로 남았다.** 되돌린 적 없다.

| 상수 | 위치 | 값 |
|---|---|---|
| `UPSTREAM_TIMEOUT_MS` | `workers/src/index.ts:54` | `15_000` |
| `REQUEST_TIMEOUT_MS` | `src/ai/llm-decider.ts:49` | `20_000` |

"프록시가 프론트보다 짧다"는 순서도 지켜졌다(15 < 20). 이 순서가 깨지면 실패 `code`가 사라져
프론트가 왜 폴백됐는지 구분하지 못한다.

**「7초와 25초 사이가 비어 있다」는 관찰이 이 결정의 전부였다.** 상한을 25초로 둔 이유가
"느린 응답을 건지기 위해"였는데, 실측해 보니 건질 것이 그 구간에 없었다.
25초는 근거 없이 넉넉하기만 한 값이었고, 재고 나서야 그것을 알았다.

되돌리지 않은 대신 **재측정도 못 했다.** 이 수치는 2026-08-05 한 번의 측정(39건)이 전부다.
호출 예산 때문에 표본을 늘리지 못했다.
