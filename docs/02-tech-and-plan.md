| 요건 | 설계에 미치는 영향 |
|---|---|
| 웹 빌드 — 링크 클릭만으로 브라우저에서 바로 플레이 | GitHub Pages 정적 배포. 서버 프로세스 없음 |

| PC 실행 파일(.exe) 제출 불가 | Electron·Unity 네이티브 빌드 배제 |
| 전체 소스 동일 저장소 + **커밋 기록 유지** | 첫날부터 실제 리포에 커밋. 마지막에 몰아서 올리면 안 됨 |
| 저장소 공개(public) 권장 | **API 키가 리포에 절대 들어가면 안 됨** |
| 30~60초 플레이 영상 (조작·합성 금지) | 실제 플레이 화면이 60초 안에 이해되도록 UI 설계 |
| 심사 종료까지 링크 접근 유지 | 8/10 제출 후 최소 8/22까지 배포·API 예산 유지 |

### 도출되는 두 가지 결론

1. **싱글플레이 고정** — 심사자는 혼자 플레이한다. 멀티플레이는 심사가 불가능하다.
2. **LLM 호출은 프록시를 거쳐야 한다** — 정적 호스팅에 키를 둘 수 없고, 심사자에게 키를 요구할 수도 없다.

### 2.1 왜 프록시 + 폴백 하이브리드인가

프록시만 두면 심사 기간(8/10~8/22) 중 **키 만료·예산 소진·API 장애가 그대로 플레이 불가**로 이어진다.
심사자가 링크를 열었을 때 게임이 안 돌아가면 그 순간 탈락이다.

그래서 **사전생성 대사 풀을 번들에 포함**한다. 프록시가 실패하거나 예산이 소진되면
게임은 사전생성 대사 + 규칙 기반 판단으로 계속 진행된다. 체험 품질은 떨어지지만 **죽지 않는다.**

| 상태 | 동작 |
|---|---|
| 정상 | LLM이 반증 판단·밀담·투표 결정 |
| 예산 소진 / API 장애 / 오프라인 | 사전생성 대사 + 규칙 기반 결정. 상단에 안내 배너 |

폴백 풀은 D8에 LLM으로 대량 생성해 정적 JSON으로 번들한다.

### 2.2 룰 엔진을 순수 함수로 분리하는 이유

제안/반증/승패 판정은 **LLM 없이 단위 테스트로 검증 가능해야** 한다.
LLM 응답에 의존하는 로직이 룰 엔진에 섞이면 버그 재현이 불가능해진다.

```
게임 상태 + 행동  →  [순수 함수]  →  새 게임 상태
```

LLM은 "AI가 어떤 행동을 선택할지"만 결정하고, 그 행동은 룰 엔진을 그대로 통과한다.
AI가 룰을 어길 수 없다.

## 3. 스택 선택

**팀 역량 전제: 둘 다 ML/DL/LLM 프로젝트 경험 있음. 웹 프론트/백엔드는 약간 가능.**
→ 프론트엔드 개발량을 최소화하고, 차별화는 AI 레이어에 몰아넣는다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트 | React + TypeScript + Vite | 자료 최다. GitHub Pages 배포 검증됨 |
| 상태관리 | Zustand 1종 | Redux 보일러플레이트 회피. 학습 비용 최소 |
| 스타일 | CSS 변수 + 최소 컴포넌트 | UI 프레임워크 학습 시간 없음. 토큰 기반으로 통일감만 확보 |
| 룰 엔진 | 순수 TS 함수 + Vitest | ML 배경이면 로직·테스트가 가장 익숙한 영역 |
| 프록시 | Cloudflare Workers | 무료 티어. 단순 fetch 프록시라 백엔드 부담 최소 |
| LLM | Anthropic API | — |

### 3.1 화면 구성 (프론트 부담 최소화)

**단일 화면 + 패널 전환.** 라우팅 없음.

```
┌──────────────────────────────────────────┐
│  라운드 3 / 8          [정답 추리표]       │  ← 상단 바
├──────────────────────┬───────────────────┤
│                      │                   │
│   테이블 뷰           │   로그 / 밀담      │
│   캐릭터 6명 배치      │   패널             │
│   현재 차례 표시       │                   │
│                      │                   │
├──────────────────────┴───────────────────┤
│  [제안하기] [능력 사용] [밀담]              │  ← 행동 바
└──────────────────────────────────────────┘
```

애니메이션은 transform·opacity만 사용한다. 레이아웃을 움직이는 연출은 넣지 않는다.

## 4. LLM 사용 방침

### 4.1 모델

**기본값: `claude-opus-5`**

10일 안에 프롬프트 튜닝 시간이 부족하므로, 모델 자체의 판단력에 의존하는 편이 안전하다.
비용·지연이 문제가 되면 D5 계측 후 조정한다 — **이건 대표님 결정 사항이다.**

주의점 (Opus 5 특성):
- **thinking이 기본 ON.** `max_tokens`는 thinking + 응답 합산 상한이므로 여유 있게 잡는다
- `effort`는 `low` / `medium`부터 시작. Opus 5는 저효율 구간 성능이 좋다
- 프롬프트 캐시 최소 512 토큰 — 시나리오·룰 설명 프리픽스가 캐시된다
- `temperature` / `top_p` 미지원. 성격 차이는 프롬프트로 만든다

### 4.2 호출 구조

| 시점 | 호출 | 캐시 |
|---|---|---|
| 반증 판단 | 에이전트당 1회 (구조화 출력) | 시나리오+룰 프리픽스 캐시 |
| 밀담 | 플레이어 발화당 1회 | 에이전트별 대화 히스토리 캐시 |
| 최종 투표 | 에이전트당 1회 | 동일 |

**프롬프트 캐싱이 비용 통제의 핵심.** 시나리오 설명·룰 설명·캐릭터 설정은 매 호출 동일하므로
프리픽스에 두고 캐시 브레이크포인트를 건다. 변동 정보(현재 라운드, 관측 로그)는 그 뒤에 붙인다.

### 4.3 구조화 출력

반증 판단·투표는 자유 텍스트가 아니라 **스키마 강제 출력**으로 받는다.
파싱 실패로 게임이 멈추는 경우를 없앤다.

```
{ "refute": true, "card": "서재", "is_lie": false, "line": "서재 카드 있습니다." }
```

### 4.4 예산 통제

- Workers에 일일 토큰 예산 캡. 초과 시 즉시 폴백 모드 신호
- IP별 레이트리밋 (플레이 세션 단위)
- D5에 1판 실측 비용을 산출하고 심사 기간 총예산을 역산한다

## 6. 2인 분업

두 사람 모두 LLM에 강하고 프론트에 약하므로, **약한 영역을 한 사람에게 몰지 않는다.**
UI를 담당하는 쪽도 콘텐츠·문서로 균형을 맞춘다.

### A — 게임 엔진 / AI 레이어

- 룰 엔진 (제안·반증·승패 판정) + 단위 테스트

- 사전생성 폴백 풀 생성 파이프라인
- 제출물 ④ **AI 활용 기술 문서**

### B — UI / 콘텐츠 / 제출물

- React UI (테이블 뷰·추리표·밀담 패널)
- 상태 연결 (Zustand)
- 시나리오 콘텐츠 (캐릭터 6명 · 비밀 · 동기 · 카드 구성)
- 직업 5종 밸런싱 데이터
- 제출물 ③ **게임 소개 문서**, ⑤ **팀원 롤 기술서**
- 제출물 ② **플레이 영상** 촬영·편집

### 공동

- D1 룰 확정 · 데이터 스키마 합의
- D8 밸런싱 (실제 플레이 반복)
- D9~D10 최종 점검

### 7.1 D1에 배포부터 뚫는 이유

GitHub Pages 배포는 base path·라우팅·빌드 설정에서 막히는 경우가 잦다.
**마지막 날에 발견하면 되돌릴 시간이 없다.** 빈 화면이라도 첫날 접속에 성공시켜 두고,
이후 매일 커밋할 때마다 자동 배포되게 한다. 커밋 기록 요건도 자연히 충족된다.

### 7.2 D3의 의미 — 첫 번째 안전선

**D3 끝에 LLM 없이 1판 완주가 안 되면 일정을 재조정한다.**
이 시점에 게임이 안 돌아가면 LLM을 붙여도 안 돌아간다.
규칙 기반 AI로 완주 가능한 빌드는 그 자체로 최악의 경우 제출 가능한 상태이기도 하다.

### 7.3 D8의 의미 — 두 번째 안전선

폴백 풀이 D8에 완성되면, 이후 API에 무슨 일이 생겨도 심사에 지장이 없다.
