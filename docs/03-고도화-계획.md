### 완주에 대해 — 앞선 기록의 「미확인」은 부정확했다 (2026-08-11 확인)

세션 기록들이 "완주 미확인"으로 넘겨 온 항목은 **엔진 차원에서는 이미 반증돼 있었다.**
`src/ai/autoplay.test.ts`가 정확히 그 일을 하고 있고, 테스트 7개가 전부 통과한다.

| 이미 검증된 것 | 근거 |
|---|---|
| 판이 끝까지 굴러가고 승패가 난다 | `phase === 'over'` · 승자 확정 |
| **24회차 전부 기록된다** | `rounds.length === DEFAULT_ROUNDS` |
| 60개 시드 전부 예외 없이 끝난다 | sweep 테스트 |
| 사람이 범인/시민인 판의 고발 주체가 갈린다 | `council` / `player` |
| 위증·이의제기가 실제로 발생한다 | 60판에서 확인 |

**UI 경로도 1회차를 온전히 통과하는 것을 배포본에서 확인했다** —
제안 → 반증 공개 → 이의제기 열림 → 밀담 → 다음 사람 제안까지 한 바퀴가 돌았다.
LLM 대사도 캐릭터별로 다르게 나왔다(폴백 정형문이 아니다).

**그래서 남은 진짜 미확인은 하나다.** `autoPlay`는 `Decider`를 인수로 받지 않는 규칙 기반 전용이라
(그 함수의 존재 이유가 "규칙 기반만으로 완주"이므로 의도된 설계다),
**LLM을 붙인 채 24회차를 끝까지 가는 경로는 이 테스트가 덮지 않는다.**
LLM 경로는 타임아웃·폴백 전환이 섞여 실패 양상이 다르므로 별도로 봐야 한다.

### 화면의 「라운드 1/4」는 라운드가 아니라 사이클이다 (2026-08-11 확인)

플레이 중 라운드 표기가 `1/4`인 채로 제안자가 나 → 참가1로 넘어갔다.
**한 사이클 안에서 6명이 각각 제안하고, 4사이클 × 6명 = 24회차**다.
`DEFAULT_ROUNDS = 24`와 맞아떨어진다.

### 문서와 코드가 어긋난 곳

- ~~`README.md`의 **「라운드 8」**~~ — **2026-08-13 해소.** 24회차 = 4라운드로 고쳐져 있다.
- ~~`README.md`의 성격·신뢰도 「미구현」 표기~~ — **2026-08-13 확인 후 고침.**
  말투는 `content/voice.ts`로 좌석 6인이 갈리므로 구현이다. 성격(거짓말 성향)은 미구현이 맞다 —
  `workers/src/prompt.ts`의 `buildMessages()`가 좌석별 성격 인자를 받지 않아 프롬프트가 전원 같다.
  신뢰도는 `feat/engine-trust-ledger`에 순수 함수만 있고 미병합이라 미구현이 맞다.
- `README.md`의 **「지금 AI를 움직이는 것은 LLM이 아니라 규칙 기반」** — **2026-08-13 해소.**
  LLM 연동 전 문장이 남아 있었다. 실제로는 `GameScreen.tsx`가 `llmDeciderForRound`를 꽂는다.

## 3. Phase 1 — 포폴 완성 (3~4주)

게이트 0을 통과했다는 전제. **보여줬을 때 완성돼 보이는 상태**가 목표다.

### A. 게임 내용

| 항목 | 지금 | 목표 | 왜 |
|---|---|---|---|
| **신뢰도 누적** | 없음 | 위증 발각·이의제기 성패가 이후 AI 판단에 남는다 | 지금은 라운드 간 기억이 얕아 심리전이 얇다. **이 게임의 코어가 사는 지점** |
| **에이전트 성격** | 폴백 대사만 갈림 | 거짓말 성향·화법을 프롬프트로 분리 | 5명이 비슷하게 말하면 "AI 5명"이 아니라 "AI 1명 ×5"로 읽힌다 |
| **시나리오** | 4 | 6 | 12개는 상용 단계에서. 포폴엔 6개면 충분하다 |
| **직업 밸런싱** | 10종 배정 확률만 확인 | 승률 기반 조정 | 오프라인 시뮬레이션으로 잰다 (LLM 비용 0) |

**신뢰도를 1순위로 둔 이유**: "거짓 반증"이 코어인데, 거짓말한 사람을 이후에 어떻게
대하는지가 게임에 반영되지 않으면 위증이 그 라운드에서 소비되고 끝난다.
누적되어야 "쟤는 이미 두 번 걸렸다"는 판단이 생기고, 그때 비로소 심리전이 된다.

### B. 디자인

아래는 배포본 화면 5장을 직접 보고 적은 것이다. 못 본 화면(반증 공개·판결)은 제외했다.

| # | 관찰한 문제 | 방향 |
|---|---|---|
| D-1 | **테이블 화면에 시선 우선순위가 없다.** 좌측 참가자 5명과 우측 추리표가 같은 무게로 깔려 있어, 처음 보면 어디부터 볼지 모른다 | 지금 차례인 것 하나만 밝히고 나머지는 눌러 대비를 만든다 |
| D-2 | **참가자가 「참가1·참가2」로 표시된다.** 캐릭터 이름(임세라)이 부제로 작게 붙어 몰입이 깨진다 | 이름을 주(主)로, 참가 번호를 보조로 뒤집는다 |
| D-3 | **추리표가 스프레드시트로 보인다.** 1935년 경성이라는 톤과 어긋난다 | 수첩·괘지 질감으로. 체크 표시도 손으로 그은 흔적처럼 |
| D-4 | **테이블 중앙 일러스트가 거의 안 보인다.** 어둡게 깔려 공간감이 죽었다 | 중앙을 비우지 말고 판의 무대로 쓴다 |
| D-5 | **밀담 패널이 빈 채로 큰 자리를 차지한다.** 라운드 끝에만 열리는데 항상 떠 있다 | 닫힌 상태를 접고, 열릴 때 존재감을 준다 |

**공통 원칙**: 지금 화면은 정보를 다 보여주지만 **무엇이 중요한지는 안 알려준다.**
정보를 빼는 게 아니라 층을 나누는 작업이다.

기존 제약은 유지한다 — `transform`·`opacity`만 쓰는 애니메이션, CSS 변수 토큰,
UI 프레임워크 미도입.

## 7. 우선순위 한 줄

> **완주 확인 → 원가 측정 → 신뢰도 → 테이블 화면 정리 → 데모.**

이 순서를 지키는 이유는 뒤로 갈수록 되돌리기 비싸기 때문이다.
완주가 안 되면 신뢰도를 넣어도 볼 수 없고, 원가를 모르면 상용 설계를 시작할 수 없다.
