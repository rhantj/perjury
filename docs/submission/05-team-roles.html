1.1약점을 나눠 가졌다

두 사람 모두 LLM에 강하고 프론트엔드에 약했다. 그래서 약한 영역을 한 사람에게 몰지 않는 것을 분업의 첫 원칙으로 삼았다. UI를 맡은 쪽이 콘텐츠·제출물로 균형을 잡고, 엔진을 맡은 쪽이 프록시·폴백까지 안는다.

경계는 말이 아니라 브랜치 이름에 박아 두었고, 커밋 기록이 그 경계를 그대로 증명한다.

3. 분업 경계위증 PERJURY 팀원 롤 기술서
3분업 경계 브랜치 이름에 박아 둔 소유권
3.1브랜치 이름이 곧 담당표다

브랜치는 <type>/<scope>-<요약> 형식으로만 만든다. 브랜치 이름만 보고 누구 작업인지 알 수 있어야 한다는 것이 규칙의 목적이다. 

feat/engine-refutation-order   → A · 룰 엔진
feat/ui-table-view             → B · 화면
fix/proxy-cors-origin          → A · 프록시
docs/ai-tech-doc               → B · 제출물
3.2scope 목록
scope범위담당
engine룰 엔진 — 제안·반증·승패A
agent에이전트 상태·프롬프트·신뢰도A
proxyCloudflare WorkersA
fallback사전생성 대사 풀A
uiReact 화면·상태 연결B
content시나리오·캐릭터·밸런싱 데이터B
docs문서·제출물B
infra빌드·CI·배포 설정공동
한 브랜치는 한 가지 일만

범위가 늘어나면 새 브랜치로 쪼갠다. 브랜치는 하루 이상 묵히지 않고, 길어지면 매일 git pull --rebase origin main으로 최신화한다. 병합된 브랜치는 바로 지운다.

4. 협업 방식위증 PERJURY 팀원 롤 기술서
4협업 방식 두 사람이 같은 리포를 동시에 미는 법
4.1푸시 = 배포

main은 배포 브랜치다. 푸시하는 순간 심사용 링크가 바뀌므로 직접 커밋하지 않는다. 작업은 각자 브랜치에서 하고, 합치기 전에 git pull --rebase origin main으로 최신화한 뒤 합쳐진 상태에서 빌드를 다시 돌린다. 각자 브랜치에서 통과해도 합치면 깨질 수 있고, 그대로 올리면 라이브가 멈춘다.

4.2기록 남기기

최신화는 --rebase(머지 커밋 노이즈 제거), main 통합은 --no-ff(작업 단위를 기록에 보존).

--force 푸시는 금지

상대의 커밋을 지우고 제출 요건인 커밋 기록을 훼손한다. 병합 커밋 128건이 그대로 남아 있는 이유다.

4.3결정 기록

아키텍처·데이터 모델·외부 연동이 바뀌면 docs/decisions/에 한 파일 한 결정으로 남긴다. 맥락 / 선택 / 버린 대안 / 되돌리는 법을 적는다. 현재 11건 — LLM 모델 선정, 프록시 상류, 폴백 범위, 밀담 횟수, 조기 고발 등.

4.4세션 인수인계

대화·작업 맥락은 하루가 지나면 사라진다. 그래서 session-resume/에 「지금 어디까지 했고 다음에 어느 파일 몇 번째 줄부터 손대는가」를 남긴다. 막힌 것은 증상·시도한 것·남은 가설 순으로 적어 상대가 같은 벽에 다시 부딪히지 않게 한다. 현재 31건이며 두 사람 모두 작성한다.

4.5공유 규칙

리포 루트 CLAUDE.md에 절대 규칙 6개(키 격리, 룰 엔진 순수성, LLM 응답 렌더링 방식, 폴백 보존, 배포 경로, 개인 작업공간 분리)와 코드·커밋·브랜치 규약을 둔다. 문서와 충돌하는 구현은 코드가 아니라 문서를 먼저 고친다.

4.6검증 게이트

npm run typecheck · npm run worker:typecheck · vitest · npm run build가 푸시 전 필수. 룰 엔진은 테스트를 먼저 쓰고 구현한다(564개).

동작 확인은 배포 링크에서

로컬 개발 서버가 아니라 배포 링크에서 확인한다 — 심사자가 보는 것이 배포본이고, 로컬에서만 되는 것은 되는 게 아니기 때문이다.
