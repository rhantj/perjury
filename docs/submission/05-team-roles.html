2.1경계를 브랜치 이름에 박아 뒀다

브랜치는 <type>/<scope>-<요약> 형식으로만 만든다. 브랜치 이름만 보고 누구 작업인지 알 수 있어야 한다는 것이 규칙의 목적이다. 한 브랜치는 한 가지 일만 하고, 범위가 늘어나면 새 브랜치로 쪼갠다.

scope범위담당
engine룰 엔진 — 제안·반증·승패A
agent에이전트 상태·프롬프트·신뢰도A
proxyCloudflare WorkersA
fallback사전생성 대사 풀A
uiReact 화면·상태 연결B
content시나리오·캐릭터·밸런싱 데이터B
docs문서·제출물B
infra빌드·CI·배포 설정공동
경계는 겹친다 — 일부러 그렇게 뒀다

자기 층에서 시작한 작업이 상대 층에 닿을 때 넘기지 않고 끝까지 밀었다. 2인 팀에서 인수인계 대기는 곧 정지이기 때문이다.

2.2푸시 = 배포이므로 합치는 절차를 고정했다

main은 배포 브랜치다. 푸시하는 순간 심사용 링크가 바뀌므로 직접 커밋하지 않는다. 작업은 각자 브랜치에서 하고, 합치기 전에 git pull --rebase origin main으로 최신화한 뒤 합쳐진 상태에서 빌드를 다시 돌린다. 각자 브랜치에서 통과해도 합치면 깨질 수 있기 때문이다. main 통합은 --no-ff로 작업 단위를 기록에 남기고, --force 푸시는 금지한다.
